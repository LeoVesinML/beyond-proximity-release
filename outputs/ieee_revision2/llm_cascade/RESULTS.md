# LLM cascade experiments (A2, B10) -- IEEE revision 2

Every number in this file comes from the saved JSON under
`outputs/ieee_revision2/llm_cascade/`. Tables are generated by
`scripts/run_ieee_llm_cascade.py --experiment report` from `summary.json`.

## What was and was not run

- **Qwen2.5-1.5B-Instruct was NOT run.** The HF cache holds only its tokenizer/config
  (`snapshots/989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, 11 MB, no `*.safetensors`).
  Downloading it (~3.1 GB) would exceed the ~1 GB write limit, so it was not downloaded. That means
  there is no exhaustive-1.5B MPS latency row either. The 1.5B row that appears below is
  recomputed from the saved Windows/CPU/fp32 traces (`outputs/ieee_revision/qwen25_15b_pair_v1`).
  To run it later: download the pinned revision and run the A2/B10 commands with
  `--model-path <1.5B snapshot> --model-id Qwen/Qwen2.5-1.5B-Instruct --tag qwen25_15b_bf16`.
- **Qwen2.5-7B-Instruct was run** for A2 (i)-(iii), the rerun LLM-only gate, and B10. Its
  four weight shards were in the HF cache as `*.incomplete` blobs. The SHA-256 of all four
  files equals the LFS object ids in their blob names, and the safetensors headers match
  `model.safetensors.index.json` of snapshot `a09a35458c702b33eeacc393d103063234e8bc28`. The
  cache was not modified: the model was loaded from a scratch directory of symlinks to those
  blobs. `generation_config.json` is absent from the cache, so transformers defaults were used.
  That has no effect on A2, because we checked that no "Yes"/"No" token id occurs in any prompt
  (`yes_no_token_ever_in_prompt: false`) and scoring does not go through a repetition penalty.
- **BGE proxy.** `fastembed` is not installed. The FastEmbed ONNX export
  `qdrant/bge-small-en-v1.5-onnx-q` (snapshot `52398278842ec682c6f32300af41344b1c0b0bb2`,
  already on disk under `/Users/leo/beyond-proximity-week6-person2/.cache/fastembed`) is run
  directly with onnxruntime 1.19.2, using FastEmbed preprocessing (CLS pooling, L2 norm,
  truncation 512). Reproduction check (`bge_reproduction_check.json`) on the 75 test queries:
  flat-BGE hit@1/hit@3 = 0.667/0.960, identical to the saved values. All 75 budget-3 ranked
  lists are identical. All 75 unlimited-budget candidate sets C(q) are identical; one query
  (qv2_040) swaps the order of two near-tied views, which does not change the set.

## Configuration

- Algorithm 1 config: the dev-selected config saved in `bge_frontier_v1/bge_frontier_summary.json`,
  i.e. `adaptive_mass`, tau=0.5, T=0.1, B(max_branches)=5, m(safety shortlist)=1, no fallback.
  **Its branch score is `node_text`** (BGE similarity of the query to the branch text), not
  `max_leaf_proxy` as the task description assumed. A `max_leaf_proxy` variant with the same
  tau/T/B/m is reported as a sensitivity row; it was not dev-selected. C(q) is taken with no candidate
  budget (the frontier's `budget_unlimited` set). N_q = |C(q)|.
- Qwen relevance scoring: same system prompt, user prompt, `compact_view` serialization,
  `C{i}` aliases over sorted candidate ids, and 2-way softmax over the {No, Yes} next-token
  logits as `scripts/run_instruction_agent_benchmark.py`. Each condition makes one batched
  forward over all of its candidates. Implementation differences from the original script (all
  forced by MPS or numerics, none by choice of method):
  1. **Right padding with a forward pass** instead of left-padded `generate(max_new_tokens=1)`. On
     MPS (torch 2.7.1), left padding with SDPA gave NaN logits for every padded row in both fp16
     and bf16. Eager attention in fp16 gave NaN even without padding. With causal attention, the
     logits at each row's last real token are the same quantity as the first generation step.
     0 NaN rows were observed in the final run.
  2. The Yes/No logits are recomputed in float32 from the final hidden state.
  3. Candidates are ranked by the log-odds (Yes minus No logit). This is monotone in p(Yes)
     but does not saturate to 1.0 in float32; with 7B, many p(Yes) values round to exactly 1.0.
     No tied log-odds occurred in any of the 1,000 A2 calls.
  4. The original saved view-grounding call kept only its top-3 IDs, so its "MRR" is MRR@3. Here
     the full ranking is kept. We report MRR over the full ranking and MRR@3; the k=3 rows
     truncate the ranking after Qwen reranking.
- dtype: **bfloat16** (the checkpoint's native dtype). A 4-query smoke test in fp16 gave the
  same rankings and a maximum |p(Yes)| difference of 1.2e-4, at the same speed.
- B10 prompt: system "You select the single scene record that best answers a query. Answer with
  the record ID only." User: query, then `[i] <compact_view record>` lines in ascending view-ID
  order for every condition (so rank order is not leaked), then an instruction to output only
  the record ID. Greedy decoding with two decoders:
  (1) free generation (12 tokens) parsed to the first valid in-context ID, where an invalid
  output counts as wrong;
  (2) trie-constrained greedy decoding (`prefix_allowed_tokens_fn`), which can only emit one
  in-context ID.
  The first free-parse-only B10 run is kept in `qwen25_7b_bf16/superseded_b10_free_parse_only/`.
  It was superseded because most of its all-records failures were formatting errors (for
  example `v0010`). The constrained decoder was added after we saw that run.

## Accounting definitions

- *retained*: records kept after the pipeline. The full-ranking rows keep |C|; the k=3 rows keep
  min(3, |C|).
- *scored/query*: records Qwen scores (candidate prompts).
- *input tok/query*: exact Qwen tokenizer count of all rendered prompts, without padding.
- *calls/query*: batched Qwen forward calls. The rerun gate uses 2: zones, then views.
- *median/mean ms*: Qwen wall-clock per query, measured from tokenization to results on the
  host after `torch.mps.synchronize()`.
- *e2e ms*: Qwen time plus BGE single-query encoding and selection. The view and branch
  embeddings are precomputed offline and are not included.

## Caveats

- Latency was measured on a shared, non-isolated laptop. During the A2 run, another CPU-bound
  experiment (`scripts/run_ieee_scale_hierarchy.py`) and desktop apps were also running. Qwen
  work is on the GPU, so the effect is probably small, but it was not controlled. Relative
  latency follows the prompt-token count closely.
- The all-125 results include the 50 dev queries that were used to select the Algorithm 1
  config. Only the test-75 results are held out.
- The 1.5B row (iv) comes from different hardware and software (Windows CPU fp32, torch 2.13,
  transformers 5.14.1, left-padded generate). Its latency is not comparable to the MPS rows.
- A2 cascades reuse one BGE ranking. In the 9.48-record regime, C(q) and flat top-N_q have
  the same size by construction, so the two cascades differ only in which records they contain.
- B10 differences come from one model, one prompt, and one record ordering. The free-parse
  numbers reflect instruction following as well as selection quality. The constrained numbers
  isolate selection quality.

## Key findings (test 75 unless stated)

- A2, Qwen2.5-7B: Algorithm 1 C(q) -> Qwen reaches hit@1 0.653, hit@3 0.947 and MRR 0.793, scoring 9.48 records per query
  (1,090 input tokens, median 2.87 s). Exhaustive Qwen reaches 0.627 / 0.973 / 0.796 over 19.4 records per query
  (2,236 tokens, median 5.68 s). Differences for (iii)-(i): hit@1 +0.027 [-0.040, +0.107], hit@3 -0.027 [-0.067, +0.000],
  MRR -0.003 [-0.045, +0.039]. Neither difference is significant, and the hit@3 CI upper bound is 0.
- The size-matched flat BGE top-N_q cascade (ii) is equal to or slightly better than Algorithm 1 at the same cost:
  (iii)-(ii) hit@1 +0.000 [-0.067, +0.067], hit@3 -0.013 [-0.040, +0.000]. On this benchmark the hierarchy
  gives no measurable benefit over a flat BGE shortlist of the same size when an LLM reranks.
- At k=3 before reranking, the paper's budget-3 set and flat top-3 give identical quality (0.640 / 0.960).
- The rerun LLM-only two-branch gate (7B) scores hit@3 0.880. Algorithm 1 minus gate: hit@3 +0.067 [-0.013, +0.147],
  while using fewer tokens (1,090 vs 1,767) and fewer calls (1 vs 2).
- The max_leaf_proxy sensitivity variant (not dev-selected) reaches hit@1 0.693 / hit@3 0.960 at 13.47 records per query.
- B10 (7B, constrained decoding): top-3 from Algorithm 1 gives accuracy 0.733, flat top-3 gives 0.733, and all records give 0.613.
  (b)-(a) = +0.120 [+0.013, +0.227]; (b)-(c) = +0.000 [-0.040, +0.040]. Free-parse gives 0.720 / 0.707 / 0.587,
  with (b)-(a) +0.133 [+0.027, +0.240]. The benefit comes from shortening the context, and flat BGE top-3 gets it too.
- Note: with 7B, exhaustive hit@1 on test (0.627) is lower than the saved 1.5B CPU run (0.733).
